# Database Design

## Schemas

| Schema | Purpose |
|---|---|
| `raw` | Bronze layer. Data loaded by the Python ingestion service, already schema/type validated but not yet modeled for analytics. |
| `staging` | dbt staging + intermediate models. Still close to source shape, renamed/typed consistently. |
| `warehouse` | Gold layer. The star schema: `dim_*` and `fact_sales`. |
| `analytics` | Reserved for reporting views built on top of `warehouse` (currently the dashboard and `sql/analytics/*.sql` query `warehouse` directly - see Future Enhancements). |
| `audit` | Pipeline run history, data quality results, rejected records. |

## Why PostgreSQL schemas instead of separate databases

Separate schemas in one database keep foreign keys and joins simple
(you can join `warehouse.fact_sales` to `raw.customers` in a debugging
query without cross-database tooling) while still giving each layer a
clear namespace and independent access control if needed later.

## Star schema

**Grain of `fact_sales`:** one row = one product line item within one
order (one row of `raw.order_items`, enriched with dimension keys).

Dimensions:

- `dim_customer`, `dim_product`, `dim_store` - classic Type 1 (overwrite
  on change) dimensions. There's no history tracking (no SCD Type 2) -
  see Future Enhancements.
- `dim_date` - a standard calendar spine, generated with
  `generate_series` rather than a dbt package, since a date range this
  small doesn't need one.

### Surrogate keys vs. natural keys

Every dimension has:
- a **surrogate key** (`*_key`, e.g. `customer_key`) - an integer
  generated by the warehouse, used for joins in `fact_sales`.
- a **natural key** (`*_id`, e.g. `customer_id`) - the original ID from
  the source system, kept as a unique column for lookups and debugging.

Surrogate keys mean the warehouse doesn't break if a source system ever
changes its ID format, and they're smaller/faster to join on than a
composite or text-based natural key.

## Normalization

`raw.*` tables are close to third normal form, matching the source
systems. `warehouse.fact_sales` is deliberately denormalized (star
schema) - dimension attributes like `product_name` and `category` live
in `dim_product`, not duplicated onto every fact row, but the fact table
itself intentionally trades some normalization for query simplicity
(that's the point of a star schema: fewer joins for common questions
like "revenue by category").

## Keys, constraints, indexes

- Every `raw.*` and `warehouse.*` table has an explicit primary key.
- Foreign keys enforce that `fact_sales` rows always point at real
  dimension rows (`store_key` is nullable since an order's store can be
  unknown, but the others are required).
- `fact_sales` has a `UNIQUE (order_id, order_item_id)` constraint - this
  is what makes reloading the same order idempotent (see
  `docs/pipeline.md`).
- `CHECK` constraints enforce basic business rules at the database level
  as a last line of defense (`quantity > 0`, amounts `>= 0`), on top of
  the validation that already happens in Python before data is loaded.
- Indexes exist on foreign key columns and on `updated_at` columns used
  for incremental loading (see `idx_raw_orders_updated_at` etc. in
  `db/init/03_tables.sql`).

## Why not VARCHAR for everything

Types are chosen to match what the data actually is:
`BIGINT` for IDs, `NUMERIC(12,2)` for money (never `FLOAT`, to avoid
rounding surprises), `DATE`/`TIMESTAMPTZ` for temporal data, `BOOLEAN`
for flags like `is_weekend`, and `TEXT` only for genuinely free-form or
short categorical strings.
